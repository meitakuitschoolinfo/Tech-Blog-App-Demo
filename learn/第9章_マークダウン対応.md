## 🐛 9-2. 何が起きていたか

詳細ページの本文に以下を投稿すると、画面では **markdown 記号がそのまま生テキスト** で表示されていました。

```markdown
# 2026年のフロントエンド開発

本文...

## 1. AI協調型開発

* 箇条書き
* 箇条書き

| col1 | col2 |
| ---- | ---- |
| a    | b    |
```

実際の見た目：「`# 2026年のフロントエンド開発` 本文... `## 1.` ...」と全部地の文。

### 原因

旧 `blog/detail.html` の本文ブロックはこうなっていました：

```html
<th:block th:each="line : ${#strings.arraySplit(blog.content, '\n')}">
    <h2 th:if="${#strings.startsWith(line, '## ')}" ...>
    <p th:unless="..." th:text="${line}">
</th:block>
```

- 行を改行で分割
- `## ` で始まる行だけ `<h2>` に
- それ以外は全部 `<p>` に **テキスト** として入れる

→ `**bold**` / `* list` / `|table|` / `---` / `#` / `###` は **全部素通り**して `<p>` の中に生表示。

### 解決策

> markdown → HTML への変換を **本物のライブラリ** に任せて、
> 出来た HTML をテンプレートに `th:utext` で出す。

これで `#` `##` `###` `**` `*` `1.` `|` `---` などをすべて正しく `<h1>` `<h2>` `<h3>` `<strong>` `<ul>` `<ol>` `<table>` `<hr>` に変換できます。

## 🔀 9-3. クライアント側 vs サーバー側

| アプローチ                  | メリット                                      | デメリット                            |
| --------------------------- | --------------------------------------------- | ------------------------------------- |
| サーバー側変換（CommonMark）| **SEO 良好**（HTMLがソースに入る）／JS不要／高速| 依存が1つ増える                       |
| クライアント側（marked.js等）| 依存追加だけで動く／編集プレビューがしやすい  | 検索エンジンに HTML が見えない／JS必須|

→ **本研修ではサーバー側変換を選択**。
　 Spring Boot らしい層構造（Service で変換 → Controller で渡す → Template が描画）になる。

## 📦 9-5. 依存の追加（pom.xml）

```xml
<dependency>
    <groupId>org.commonmark</groupId>
    <artifactId>commonmark</artifactId>
    <version>0.24.0</version>
</dependency>
<dependency>
    <groupId>org.commonmark</groupId>
    <artifactId>commonmark-ext-gfm-tables</artifactId>
    <version>0.24.0</version>
</dependency>
```

### なぜ CommonMark？

| 候補         | 特徴                                                |
| ------------ | --------------------------------------------------- |
| **CommonMark Java** | 仕様準拠が高く、シンプルで軽量。拡張も豊富 |
| Flexmark     | 機能豊富だが依存が大きい                            |
| Markdownj    | 古くてメンテが弱め                                  |

→ **学習・実務両対応で迷ったら CommonMark**。

### なぜ tables 拡張を別途入れる？

CommonMark の **核（core）は仕様準拠** のため、CommonMark仕様に **無い** 機能は
別の Extension として提供されている：

- **表** (`| a | b |`) → GFM tables 拡張
- **取り消し線** (`~~text~~`) → strikethrough 拡張
- **自動リンク** (`https://...`) → autolink 拡張

ブログ記事で **表が使いたい** → tables 拡張は **ほぼ必須**。

## 🧱 9-6. MarkdownService の中身

完成ファイル：[MarkdownService.java](../src/main/java/com/meitaku/blog/service/MarkdownService.java)

```java
@Service
public class MarkdownService {

    private final Parser parser;
    private final HtmlRenderer renderer;

    public MarkdownService() {
        List<Extension> extensions = List.of(TablesExtension.create());
        this.parser = Parser.builder().extensions(extensions).build();
        this.renderer = HtmlRenderer.builder()
                .extensions(extensions)
                .escapeHtml(true)   // ★ XSS対策：生HTMLをエスケープする
                .build();
    }

    public String toHtml(String markdown) {
        if (markdown == null || markdown.isEmpty()) return "";
        Node document = parser.parse(markdown);
        return renderer.render(document);
    }
}
```

### 設計のポイント

| ポイント                              | なぜ？                                                          |
| ------------------------------------- | --------------------------------------------------------------- |
| Parser / HtmlRenderer を **field** に保持 | 毎回 build するとコスト。Bean は singleton なので使い回し安全 |
| `extensions` を **両方** に渡す       | パーサとレンダラ両方が拡張を知らないと表が動かない              |
| `escapeHtml(true)`                    | markdown内の `<script>` 等を文字列扱いに（XSS対策）             |
| `null/空文字ガード`                   | Controller / Template での if 分岐を減らす                      |
| `@Service` だけ／`@Transactional` 無し | DB アクセスしないので不要                                       |

### `escapeHtml(true)` の威力

入力：
```markdown
本文に <script>alert(1)</script> を含む
```

| 設定                          | 出力 HTML                                       |
| ----------------------------- | ----------------------------------------------- |
| デフォルト（escapeHtml=false）| `<p>本文に <script>alert(1)</script> を含む</p>` ← **危険**|
| `escapeHtml(true)`            | `<p>本文に &lt;script&gt;alert(1)&lt;/script&gt; を含む</p>` ← **安全** |

→ 管理者が信頼できる前提でも、**習慣としてON**。

## 🎮 9-7. Controller の変更

完成ファイル：[BlogDetailController.java](../src/main/java/com/meitaku/blog/controller/blog/BlogDetailController.java)

### 旧

```java
@GetMapping("/blogs/{id}")
public String detail(@PathVariable Long id, Model model) {
    Blog blog = blogService.findById(id);
    model.addAttribute("blog", blog);
    return "blog/detail";
}
```

### 新

```java
@GetMapping("/blogs/{id}")
public String detail(@PathVariable Long id, Model model) {
    Blog blog = blogService.findById(id);
    model.addAttribute("blog", blog);
    // ★ markdown を HTML 文字列に変換してモデルに入れる
    model.addAttribute("contentHtml", markdownService.toHtml(blog.getContent()));
    return "blog/detail";
}
```

### なぜ blog.content を直接 template で変換しない？

- テンプレートは **「描画専用」**。ロジック（変換）は持たせない
- Service を呼ぶ層は **Controller の責務**
- → 「**ロジックは Service、描画は Template**」 の原則

## 🧩 9-8. ★最重要★ Template での `th:text` と `th:utext` の違い

完成ファイル：[blog/detail.html](../src/main/resources/templates/blog/detail.html)

### 旧

```html
<p th:text="${line}">段落</p>
```

### 新

```html
<div class="markdown-body" th:utext="${contentHtml}">
    本文HTML
</div>
```

### `th:text` vs `th:utext` 早見表

| 属性         | 動作                                          | 例                                           |
| ------------ | --------------------------------------------- | -------------------------------------------- |
| `th:text`    | 中身を **HTMLエスケープ** して描画           | `<b>X</b>` → 「`<b>X</b>`」（タグも文字に） |
| `th:utext`   | 中身を **エスケープせず生のHTML** として描画 | `<b>X</b>` → **X**（太字）                  |

→ `th:utext` は便利だが、信頼できない文字列に使うと **XSS 直行**。
　 今回は **MarkdownService 側で escapeHtml(true)** が効いているので安全。

### 「`u` は何の略？」

- `utext` の `u` = **unescaped**
- 「エスケープ無し」を明示する命名

## 🎨 9-9. Tailwind 流の typography 無しで素のCSSで装飾

### なぜ素のCSS？

- Tailwind 公式の `@tailwindcss/typography` プラグインは **CDN 構成では使いづらい**
- ビルド環境を整えるのは研修としてオーバースペック
- → **`<style>` ブロックで .markdown-body 配下を直接スタイル** するのが一番シンプル

### CSS の構造

```css
.markdown-body h1 { ... }
.markdown-body h2 { border-bottom: 2px solid #e2e8f0; ... }
.markdown-body ul { list-style: disc; padding-left: 1.75rem; ... }
.markdown-body table { border-collapse: collapse; ... }
.markdown-body pre  { background: #0f172a; color: #f1f5f9; ... }
.markdown-body code { background: #f1f5f9; color: #db2777; ... }
.markdown-body hr   { border-top: 1px solid #e2e8f0; ... }
```

`.markdown-body` という **クラスでスコープを限定** することで、
他のページの h1/h2/p 等に影響を与えずに済む。

### 主要要素の対応表

| markdown 記法      | 出力 HTML       | このCSSでの見た目                       |
| ------------------ | --------------- | --------------------------------------- |
| `# 見出し`         | `<h1>`          | 大見出し（フォント大／太字）            |
| `## 見出し`        | `<h2>`          | 中見出し（下線付き）                    |
| `### 見出し`       | `<h3>`          | 小見出し                                |
| `**強調**`         | `<strong>`      | 太字（濃色）                            |
| `* リスト`         | `<ul><li>...`   | 黒丸の箇条書き                          |
| `1. 番号`          | `<ol><li>...`   | 数字付きリスト                          |
| `> 引用`           | `<blockquote>`  | 左に水色のバー                          |
| `` `code` ``       | `<code>`        | ピンクの等幅                            |
| ```` ```code``` ```` | `<pre><code>` | 濃紺背景の整形済みブロック              |
| `[text](url)`      | `<a>`           | 青下線リンク                            |
| `---`              | `<hr>`          | 薄い水平線                              |
| `| a | b |` (表)   | `<table>`       | 罫線付き表（ヘッダ背景・縞模様）        |

## 🛡 9-10. XSS のリスクと対策（補足）

### リスクの場面

- 管理者がうっかり/悪意で `<script>` を markdown に書き込む
- それが詳細ページで生 HTML として実行される

### 二重防御の構造

```text
[管理者入力]
   │
   ▼
[Service: MarkdownService]
   ├─ Parser.parse(...)
   └─ HtmlRenderer (escapeHtml=true) ← ★ 第1の防御
   │     <script> → &lt;script&gt; に変換
   ▼
[Template: th:utext]
   ※ ここでエスケープを外して描画
   ※ 上で既に文字列化済みなので、もう <script> はタグとして発火しない
   ▼
[ブラウザ]
   <p>&lt;script&gt;alert(1)&lt;/script&gt;</p>
   ↑ そのまま「文字列として表示」される
```

→ **MarkdownService 側で必ず `escapeHtml(true)`** にしてから `th:utext` を使う。

## ❌ 9-11. つまづきやすいポイント

| 症状                                                | 原因                                                          |
| --------------------------------------------------- | ------------------------------------------------------------- |
| 画面に `<h1>...` 等が **タグごと文字で出る**         | テンプレートが `th:text` のまま（→ `th:utext` に変更）         |
| `# 見出し` 等が markdown 記号のまま                  | Controller で `markdownService.toHtml(...)` を呼んでいない    |
| 表が罫線なし、ただの「`|a|b|`」表示                  | `commonmark-ext-gfm-tables` 拡張を読み込んでいない            |
| 見出しのフォントが大きくならない                     | `.markdown-body` クラスを `<div>` に付け忘れている            |
| `<script>` がブラウザで実行されてしまう              | `escapeHtml(true)` 設定漏れ／別の入力経路から HTML が流入     |
| 改行が無視される（段落で離れない）                   | CommonMark 仕様：**1行改行は段落区切りにならない** → 空行を入れる |

## ✨ 9-13. ポイント（必読）

### ポイント①：**「描画系の出力で何を使うか」を反射で選べるように**

- 純粋テキスト → `th:text`
- HTML（信頼できる） → `th:utext`
- 信頼できないHTML → 一度サニタイズしてから `th:utext`

### ポイント②：**markdown 変換は Service で**

Controller でも Template でもなく **Service**。
理由：テストしやすい／再利用しやすい／責務が明確。

### ポイント③：**Parser/HtmlRenderer はインスタンスを使い回す**

毎回 build すると無駄。final で1回作って使い回す。

### ポイント④：**escapeHtml(true) を必ずONに**

「管理者しか書かないから大丈夫」と思っても、習慣として ON。
クッキーを盗られる事故は **1回でも致命的**。

### ポイント⑤：**表が出ないときは GFM tables 拡張を疑う**

CommonMark 仕様に **表は無い**。拡張を入れないと表が動かない。

### ポイント⑥：**改行は「空行」で段落区切り**

CommonMark 標準では「1回の改行」は段落区切りにならない。
段落を分けたいときは **空行を入れる**。

### ポイント⑦：**CSSスコープを `.markdown-body` で囲う**

ページ全体の h1/h2/p 等に影響を出さないため。
管理画面のテーブルなどが意図せず装飾されないようにする。
